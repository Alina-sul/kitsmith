--------------------------------------------------------------------------------
1. PRODUCT
--------------------------------------------------------------------------------

rytmdash is a native macOS desktop app (Rust + egui) that turns the Elektron
Analog Rytm MKII drum machine into something manageable from a computer:

  * Plug the Rytm in over USB -> the app recognizes it automatically.
  * One click pulls the device's active project (kits, patterns, sounds,
    sample slots) into a local model and renders it as a dashboard.
  * The dashboard mirrors the hardware: the selected kit is shown as the
    12-pad grid in the machine's physical layout.
  * Sample management actions are drag & drop: drag a sample-slot chip onto
    a pad to re-point that track's sample. Every device write is a previewed,
    verified, backup-protected transaction.
  * WAV files dropped on the window are converted to the Rytm's native format
    and can be uploaded to the device.

Long-term goal (roadmap, not built): move samples and entities BETWEEN
projects with automatic slot/reference bookkeeping — the thing that is
practically impossible on the hardware.

1.1 The problem
The AR's data model has a 4-level indirection:

  pattern -> kit (1 of 128, by slot number)
          -> Sound (12 per kit, one per drum track)
          -> project sample slot (1..127, referenced BY NUMBER)
          -> +Drive file (1 GB internal storage, never mounted as a disk)

Nothing on the device or in Elektron's official Transfer app shows "what uses
what". Replacing or moving a sample slot silently changes/breaks every kit
that references that number. Cross-project moves require sysex gymnastics and
break references. rytmdash's core value = making this reference graph visible
and its mutations safe.

1.2 Non-goals (v1)
  * Audio streaming / Overbridge (audio-over-USB) — out of scope.
  * Pattern/sequence editing — out of scope for now.
  * Editing synth parameters from the app — the dashboard reads them only.

2. DOMAIN BACKGROUND (device facts the code relies on)
--------------------------------------------------------------------------------

Sources: official AR MKII User Manual OS 1.72 (local copy: reference/, git-
ignored; URL in docs/research/), Elektron Transfer behavior, and community
reverse engineering. Deeper writeups: docs/research/current-usage-flow.md and
docs/research/protocol-ecosystem.md (in-repo).

  * +Drive: 128 project slots; sample bank as a directory tree (FACTORY/
    write-protected, INCOMING/ = default computer-upload target, RECORDED/ =
    on-device sampling target, user dirs); Sound library (4096 sounds).
  * Project: 128 patterns, 128 kits, 16 songs, 4 globals, 128-slot Sound
    pool, 127 sample slots, <= 64 MB sample RAM.
  * Kit: 12 track Sounds + FX track + scenes + performance macros.
  * Sound: machine choice (synth engine per track, e.g. BdHard, SdClassic)
    + parameter pages + a SAMPLE SLOT NUMBER (SMPL page). Wire values 0 and
    0xFF both appear to mean "no sample" (assumption, flagged for hardware
    verification).
  * Native sample format: 16-bit / 48 kHz / mono WAV. Transfer converts on
    import; rytmdash does the same.
  * Track order (pads left->right, bottom row first):
    BD SD RS CP | BT LT MT HT | CH OH CY CB   (indices 0..11)
  * Pattern naming as shown on device: banks A..H x 16 -> "A01".."H16".
  * The device speaks TWO unrelated sysex protocols over USB-MIDI (see §6).
    Samples never move over the object protocol; kit/sound objects never move
    over the file protocol.
  * MIDI+USB port config throttles USB; USB-only recommended for transfers.
  * Firmware: device OS 1.72; the rytm-rs library targets FW 1.70 — object
    formats must be round-trip-verified on hardware before write features are
    trusted (Section 9).

--------------------------------------------------------------------------------

PR stack (each stacked on the previous; merge #1 first, then retarget):

  #2 milestone/m2-read-active-project — object sync, model, cache, dashboard
  #3 milestone/m4-import-sds          — audio conversion + SDS sample upload
  #4 milestone/m5-ops-dragdrop        — transaction ops + drag&drop writes
  #5 milestone/ui-pad-grid            — pad-grid UI redesign + hotplug fix
  #6 milestone/file-protocol-read     — file protocol: sample names, projects

3.1 Device recognition (PR #1, fix in #5)
  * Background watcher thread polls MIDI ports every 1 s.
  * A port whose name contains "rytm" (case-insensitive) = the device.
  * On appearance: MIDI Device Inquiry handshake (universal sysex); if the
    device answers, manufacturer/family/member/OS-version are parsed and
    shown; if not, it degrades to name-only recognition (still connected).
  * Unplug detection by port disappearance.
  * macOS gotcha (fixed): CoreMIDI only refreshes a process's port list if
    the thread that made the FIRST CoreMIDI call services a CFRunLoop. The
    first call is therefore made on the main thread (gui/mod.rs run())
    before the watcher spawns. Without this, devices plugged in after app
    launch are never seen.

3.2 Project sync — read path (PR #2, extended #6)
  * "⟳ Sync" pulls the ACTIVE project over the object protocol via rytm-rs:
    128 kits + 128 patterns + 128 pool sounds (384 request/reply round
    trips), each with a 2 s reply timeout; unanswered objects are counted
    ("missed"); 8 consecutive silents aborts; cancellable; progress bar.
  * Phase 2 (file protocol): RAM slot table -> per-used-slot hash+size ->
    +Drive path lookup -> sample NAMES; then /projects listing -> the 128
    project slot names.
  * Result is distilled into ProjectModel (src/model/) — small, serde-
    serializable — and cached as JSON at
    ~/Library/Application Support/rytmdash/active_project.json
    so the app renders instantly on next launch (cache-first design).
  * ProjectModel contents: kits (index, name, 12 sounds each with name/
    machine/sample_slot), patterns (index -> kit_index), pool sounds,
    samples[] (slot, file name, +Drive path, size), projects[] (id, name).
  * Derived views: slot_usage() = BTreeMap slot -> [ {kit, track, sound} ]
    (the "what uses what" index); linked_kit_indices() = kits any pattern
    references; sample_name(slot).

3.3 The dashboard UI (PR #5 + #6) — see §5 for exact look
  * Kit strip: selectable chips (kit name + pattern badges like "A01 A02"),
    only kits linked by patterns are listed.
  * Pad grid: selected kit as 12 tiles in hardware layout; each tile shows
    track label (colored), sound name, machine, sample chip + sample file
    name. Tiles are drag&drop TARGETS.
  * Slot rail (right panel): every used slot as a draggable purple chip with
    its file name and a xN use count. Clicking a chip "traces" it: every pad
    using that slot gets a purple highlight ring, and the rail expands to
    list its users. Clicking a pad's chip traces in reverse.
  * Projects menu (top bar): all 128 +Drive project slots by name; read-only
    reference (switch on device, then Sync — the menu says so).
  * ⋯ menu: raw MIDI input/output port lists (debugging).
  * Empty state: 1-2-3 getting-started card (connect, set USB CONFIG, sync).

3.4 Sample import + upload (PR #3)
  * Drop .wav files anywhere on the window -> conversion queue (bottom tray):
    decode (any int 8..32-bit or float WAV, any rate/channels, via hound) ->
    average-downmix to mono -> windowed-sinc resample to 48 kHz (hand-rolled,
    Hann window, cutoff at lower Nyquist, gain-normalized; quality over
    speed, runs off the UI thread) -> 16-bit PCM. Tray row shows seconds/KB/
    source format.
  * "⇪ upload" sends it via MIDI Sample Dump Standard (SDS): dump header,
    127-byte checksummed packets (40 words each), ACK/NAK-retry/WAIT/CANCEL
    handshake handling, open-loop fallback (20 ms rest) if the receiver
    never handshakes, plus the SDS sample-name extension message. Uploads
    land in the +Drive dir marked UPLOAD HERE (INCOMING/ by default).

3.5 Device writes — the transaction framework (PR #4)
  * NOTHING in the GUI writes to the device directly. A gesture compiles to
    a Plan (ordered OpSteps) -> preview modal -> execute() against the
    DeviceBackend trait -> stop at first failure -> completion report.
  * Two safety rules enforced IN THE FRAMEWORK:
    1. The session's first mutating plan auto-prepends BackupProject: a full
       raw-sysex pull of all kits/patterns/sounds/globals/settings written to
       ~/Library/Application Support/rytmdash/backups/backup-<unix>-<n>.syx.
    2. Slot writes are verified by read-back: write kit -> re-query the kit
       -> compare; mismatch fails the step.
  * Implemented write op: AssignSampleSlot { kit, track, slot } — re-points
    one kit track's Sound at a project sample slot (queries a FRESH copy of
    the kit before mutating, never a cached one, then sends the kit object).
  * LiveBackend = real implementation over the MIDI link + rytm-rs.
    MockBackend (tests) proves ordering, no-write-after-failed-backup, and
    verification-failure handling without hardware.
  * UI flow: drag chip -> drop on pad -> "Confirm change" modal (slot number
    editable, every step spelled out) -> Execute (disabled if disconnected)
    -> worker thread with per-step progress -> Done/Stopped report.


--------------------------------------------------------------------------------
4. ARCHITECTURE
--------------------------------------------------------------------------------

Library + thin binary (src/main.rs is 3 lines). Everything is in the library
so integration tests can exercise it. No unsafe. No panics on device paths —
errors degrade (name-only recognition, numbers-without-names, etc.).

src/
  config.rs        All tunable constants: poll interval 1s, inquiry timeout
                   750ms, object-reply timeout 2s, sync miss limit 8, SDS
                   handshake timeout 500ms / open-loop rest 20ms / retry 8,
                   file-protocol reply timeout 2s, Elektron manufacturer id
                   [00 20 3C], port-name hint "rytm".
  midi/            Transport, device-agnostic:
    inquiry.rs     MIDI Device Inquiry build/parse (pure).
    ports.rs       Port enumeration snapshot {inputs, outputs}.
    link.rs        MidiLink: one open in+out connection pair; received sysex
                   queued on an mpsc channel; send() + recv_timeout().
    sds.rs         Sample Dump Standard messages (pure): dump_header,
                   data_packets (checksum, 3-byte word packing), sample_name
                   extension, parse_handshake, unpack_word (test helper).
  device/          The Rytm specifically:
    detect.rs      is_rytm_port(), DeviceState { Searching | Connected },
                   DeviceInfo::describe().
    watcher.rs     Poll thread; publishes WatcherSnapshot {device, ports};
                   fires an on_change callback (GUI repaint).
    objects.rs     Object-protocol sync engine (rytm-rs): sync_active_project
                   with progress/cancel/miss-limit; accept_reply() helper.
    files.rs       File-protocol client (clean-room, see §6.2): FileClient
                   with ping / list_sample_dir / list_data_dir / ram_slots /
                   sample_path_from_hash_size; enrich_model() = sync phase 2;
                   pack7/unpack7/frame/unframe + parsers exposed for tests.
    samples.rs     SDS upload orchestration over MidiLink (handshake loop).
  model/           ProjectModel + KitModel/SoundModel/PatternModel/
                   SampleSlotInfo/ProjectInfo; slot_usage(); slot_from_wire()
                   (0/0xFF = SMP off); pattern_display_name(); serde for the
                   cache (new fields #[serde(default)] for compatibility).
  cache.rs         JSON cache dir (~/Library/Application Support/rytmdash on
                   macOS, ~/.rytmdash elsewhere); save_in/load_from take a
                   dir for testability.
  ops/             Transactions:
    mod.rs         OpStep {BackupProject, AssignSampleSlot}, Plan (validates
                   slot 1..=127, auto-prepends backup), execute() with
                   on_step progress, ExecutionReport, read-back verification.
    backend.rs     trait DeviceBackend { backup_project, write_kit_sample_
                   slot, read_kit_sample_slot } + OpError.
    live.rs        LiveBackend over MidiLink + rytm-rs.
  audio/           convert.rs (WAV -> ConvertedSample {name, pcm i16 48k
                   mono}), resample.rs (windowed sinc), constants.
  gui/             egui/eframe 0.35 app:
    mod.rs         run(): primes CoreMIDI on main thread, opens 720x480
                   window "rytmdash".
    app.rs         Shell: top status bar, bottom import tray, central
                   dashboard or empty state, execute modal; collects
                   window-dropped files.
    dashboard.rs   Kit strip + pad grid + slot rail; drag&drop; returns
                   PendingAssign to the app (never mutates).
    sync.rs        SyncController: worker thread, SyncStatus state machine,
                   cache save, file-protocol phase 2.
    import.rs      ImportPanel: conversion queue + upload workers.
    execute.rs     ExecutePanel: confirm modal, ExecState machine, worker.
    theme.rs       SLOT_COLOR purple #9B59B6, OK green #2ECC71,
                   TRACK_LABELS[12], TRACK_COLORS[12] (warm lows->cool highs).

Threading model: GUI main thread (egui immediate mode) + watcher thread +
one worker thread per long operation (sync / upload / plan execution). All
cross-thread state is Arc<Mutex<...>> snapshots read by the GUI per frame;
workers trigger repaints via egui Context::request_repaint. Each worker opens
its OWN MidiLink (CoreMIDI multiplexes fine); only one sync and one execution
can run at a time (controller guards).

Data flow (read):  device --sysex--> MidiLink --rytm-rs/parsers--> model
                   --serde--> cache --render--> egui
Data flow (write): drag gesture --> PendingAssign --> Plan --> preview -->
                   execute(LiveBackend) --> write + read-back verify -->
                   report (backup .syx on disk first).

5. UI — EXACT LOOK & INTERACTIONS
--------------------------------------------------------------------------------

Window: "rytmdash", 720x480 default, resizable; default egui dark theme.

Top status bar (always visible):
  [rytmdash] | ● Elektron Analog Rytm MKII  [⟳ Sync]        ... [projects (N)] [⋯]
  * Green dot + port name when connected (hover = identity/OS version);
    spinner + "Searching for an Analog Rytm…" otherwise (hover = device
    setup instructions).
  * Sync button becomes a progress bar ("kits 87/384", then "sample names
    12/31", "project list") with a cancel button while running. Last sync
    note ("sync complete") shows right-aligned.

Central area when a model exists:
  * Right rail "SAMPLE SLOTS — N in use · click to trace, drag onto a pad":
    rows of [⬦ 14] kick_808.wav ×3. Chip = purple rounded rectangle,
    draggable; selected chip = brighter purple; selecting expands an
    indented user list ("kit 4 MYKIT · BD").
  * Main column: "KITS" caption + hint, then selectable kit chips
    ("DEMO KICKS  A01 A02"), then "kit N · NAME", then the pad grid:
    3 rows x 4 tiles, 148x84 px each, top row CH OH CY CB, bottom row
    BD SD RS CP (hardware orientation). Tile = dark rounded rect, thin
    border; contents: colored track label top-left (BD red, SD orange, ...,
    CB violet), sample chip or "synth" top-right, sound name, machine name
    (weak), sample file name (purple, small) when known.
  * Cross-highlight: selected slot -> 2px purple ring on every pad whose
    sound uses it.
  * Drag & drop: dragging any chip shows it following the cursor; drop zones
    (pads) highlight per egui dnd; dropping opens the confirm modal.
Confirm modal ("Confirm change"): target kit/track, editable slot DragValue
  (1..127), bullet list of steps (backup line included on first write of the
  session), [▶ Execute on device] (disabled when disconnected) / [cancel].
Executing modal: spinner + "step 1/2: pull a full project object backup...".
Done/Stopped modal: ✓ lines for completed steps, ✗ + explanation on failure
  ("Nothing after the failed step ran...").
Bottom import tray (only when files were dropped): per file — name,
  "0.42s · 40 KB · from 44100 Hz/2ch", [⇪ upload] -> progress bar -> "sent ✓"
  (or "sent (open loop)") / red error text, [✕] remove.
Empty state (no model yet): centered "No project data yet" + 3 numbered
  setup steps + drop-files hint.

Design language: hardware-mirroring layout; per-track identity colors reused
everywhere; purple = anything sample-related; green = connected/success;
information density kept low — details on hover/expand.

6. PROTOCOLS IMPLEMENTED
--------------------------------------------------------------------------------

All over USB-MIDI sysex. The +Drive never mounts as a disk.

6.1 Object protocol (via rytm-rs 0.1.3 -> rytm-sys -> libanalogrytm)
  * Community reverse-engineered; targets FW 1.70 (device runs 1.72).
  * Query/response per object: kits, patterns, sounds, globals, settings
    (no songs). rytm-rs abstracts encode/decode; we provide transport.
  * Used for: full active-project pull, kit writes (slot assignment), the
    raw backup (all object replies concatenated to a .syx file).
  * Device answers on a low-priority thread — replies can be slow; we use
    per-object timeouts and never flood.

6.2 File protocol (clean-room implementation in device/files.rs)
  * The protocol Elektron Transfer speaks. Undocumented. Wire format learned
    from the elektroid project (GPLv3) used STRICTLY AS A SPEC — formats
    were extracted by reading, no code ported (license wall).
  * Frame: F0 00 20 3C 10 00 <payload> F7. Payload packs each 7 data bytes
    into 8 wire bytes: leading byte carries the 7 MSBs (first byte's MSB in
    bit 6). Decoded request: [seq_hi, seq_lo, 0, 0, opcode, args...]. Reply
    echoes seq at bytes 2-3, answers opcode|0x80 at byte 4, status at 5.
  * Implemented (read-only): 0x01 ping; 0x10 sample dir listing (entries:
    hash u32, size u32, write_protected u8, type 'D'/'F', name cstr);
    0x53 data listing with path + start/end/all args, entries from byte 18
    (name cstr, has_children, type 1=dir/2=slot, id/size/ops/valid/meta) —
    "/projects" = project slots; 0x17 RAM slot table (count u32 then 11-byte
    entries hash/size/id/used); 0x23 hash+size -> +Drive path (path cstr at
    byte 14 when status==1). Names are CP1252; decoded latin1-style.
  * NOT yet implemented: sample upload/download over this protocol, .arprj
    download, directory create/rename/delete, load-sample-to-RAM-slot.

6.3 MIDI Sample Dump Standard (midi/sds.rs) — openly documented
  * Dump header (21 bytes: sample number, 16 bits/word, period ns, length,
    loop points, loop type 0x7F=off), data packets (F0 7E cc 02 kk +120
    bytes+checksum F7; checksum = XOR of bytes 1..124 masked to 7 bits;
    16-bit words + 0x8000, left-justified in 21 bits, 3 bytes MSB-first),
    handshakes (ACK 7F / NAK 7E / CANCEL 7D / WAIT 7C), name extension
    (F0 7E cc 05 03 sl sh len name F7).

6.4 MIDI Device Inquiry (midi/inquiry.rs) — standard universal sysex.

7. QUALITY: TESTS, CI, CONVENTIONS
--------------------------------------------------------------------------------

  * 39 integration tests in tests/ (no hardware needed):
    inquiry (4), detect (3), model (6, built against rytm-rs device-default
    projects), cache (2, temp dirs), audio (5, generated WAVs; frequency
    preserved via zero-crossing analysis, amplitude via peak), sds (7,
    byte-exact fixtures), ops (5, mock backend proves transaction rules),
    files (7, synthetic wire fixtures for every parser + pack7 round trip).
  * CI (GitHub Actions): cargo fmt --check, clippy --all-targets
    -D warnings, cargo test --all-targets; on every PR and push to main;
    ubuntu runner installs libasound2-dev for midir.
  * Conventions: never commit to main; branch + PR per milestone; writes to
    the device only through ops/ transactions; constants only in config.rs;
    elektroid is GPL -> spec-only; CLAUDE.md in repo root carries the
    hard constraints for AI-assisted sessions.

Dependencies: eframe/egui 0.35 (GUI), midir 0.10 (MIDI I/O), rytm-rs 0.1.3
(AR object sysex), hound 3.5 (WAV), serde/serde_json (model/cache). That's
all — resampler, SDS, and file protocol are hand-written.

8. HOW TO BUILD / RUN / REVIEW
--------------------------------------------------------------------------------

  * Toolchain: stable Rust (source ~/.cargo/env).
  * cargo run --release  -> the app. cargo test --all-targets -> tests.
    cargo clippy --all-targets -- -D warnings must be clean (CI gate).
  * Device setup: GLOBAL SETTINGS -> SYSTEM -> USB CONFIG -> USB-MIDI;
    MIDI CONFIG -> PORT CONFIG -> INPUT FROM / OUTPUT TO -> USB (MIDI+USB
    throttles bulk transfer).
  * First run shows the empty state (or a cached/demo model if
    ~/Library/Application Support/rytmdash/active_project.json exists).
    Press ⟳ Sync with the device connected.
  * PR review order: #1 -> #2 -> #3 -> #4 -> #5 -> #6 (stacked; after
    merging one, GitHub retargets the next automatically).

9. VERIFICATION STATUS — WHAT IS PROVEN VS ASSUMED
--------------------------------------------------------------------------------

Proven offline (unit/integration tested, byte-exact where applicable):
  * All parsers/builders for all four protocols' implemented messages.
  * Model distillation + usage index + cache round-trip.
  * Audio conversion quality (pitch/amplitude preservation, format matrix).
  * Transaction ordering, backup-first rule, read-back verification logic.

Verified on hardware so far:
  * USB device recognition end-to-end (green dot on the user's AR MKII after
    the CoreMIDI main-thread fix).

NOT yet verified on hardware (the current frontier — each degrades safely):
  * Object sync against OS 1.72 (rytm-rs targets 1.70): kit/pattern/sound
    replies must parse; "missed" counter exposes failures.
  * SMP-off wire values: 0 and 0xFF both treated as "no sample" — must
    check a kit that really uses slot assignments.
  * File protocol on the AR specifically: ping/dir/projects listing shape;
    0x17/0x23 (RAM slots + hash lookup) are marked Digitakt-family in the
    reference implementation — the AR may ignore them. Fallback plan if so:
    parse the slot table out of the .arprj data file instead.
  * SDS acceptance by the AR (manual only promises the legacy C6 path):
    handshake timing, name extension support.
  * The kit WRITE path (AssignSampleSlot). Rule: first ever write on a
    scratch kit; the framework takes a full backup first regardless.

Open protocol questions:
  * Is there a safe remote "load project slot N" op? (Would enable in-app
    project switching; DATA_SWAP 0x5d exists in the reference but is
    unstudied.) Until then: switch on device + Sync.
  * .arprj internal format for non-active projects' slot tables (needed for
    cross-project views without loading each project).
